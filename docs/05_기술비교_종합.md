## 1. 한 장 요약

같은 업무(릴리즈 → 검증 → 이관 → 수정 → 재발행)를 4가지 방식으로 연결했다. 결과는 모두 같고, **"누가 흐름을 알고, 상대를 어떻게 부르고, 일이 끝난 것을 어떻게 아는가"** 만 다르다.

```text
1. Standalone   [ Dev 함수 ── QA 함수 ]                 하나의 프로그램, 함수 직접 호출
2. API          [Dev] ◀──REST/Webhook──▶ [QA]           서로의 주소와 데이터 형식을 안다
3. MCP          [Dev 도구] ◀── Host(AI) ──▶ [QA 도구]   AI가 양쪽 도구를 함수 단위로 호출한다
4. A2A          [Dev Agent] ◀── Hub ──▶ [QA Agent]      Hub가 업무 단위로 위임, 방법은 각 에이전트가 결정
```

| 관점 | 1. Standalone | 2. API | 3. MCP | 4. A2A (Hub) |
| --- | --- | --- | --- | --- |
| 프로세스 | 1개 | Hub / Dev / QA | Host / Dev MCP / QA MCP | Hub / Dev Agent / QA Agent |
| 상대를 부르는 방법 | 함수 호출 | REST 호출 | MCP `tools/call` | A2A `SendMessage`(Task 위임) |
| 상대를 아는 방법 | import | 문서·URL·스키마 합의 | `tools/list` 자동 발견 | Agent Card 자동 발견 |
| 흐름을 아는 주체 | 코드 | 각 서비스 코드(Webhook 체인) | Host의 LLM(프롬프트) | Hub 워크플로 + 각 에이전트 |
| 상호작용 단위 | 함수 | API 엔드포인트 | 도구(함수) | 업무 목표(Task) |
| 판단(LLM) 위치 | 서비스 내부 | 서비스 내부 | Host 한 곳에 집중 | 각 에이전트 + Hub에 분산 |
| DB | 단일 | 서비스별 | 서비스별 + Host 기록 | 에이전트별 + Hub(관제·감사) |
| 결합도 | 매우 강함(코드) | 강함(URL·스키마) | 중간(도구 이름·인자) | 약함(스킬 ID + 표준 Task) |
| 관계 | — | 시스템 ↔ 시스템 | 에이전트 → 도구 (수직) | 에이전트 ↔ 에이전트 (수평) |
| 장시간 작업 | 동기 호출 | Webhook 직접 설계 | 도구 호출 단위 | Task 상태 + 스트리밍 표준 |
| 승인 요청 표현 | 같은 화면에서 직접 처리 | 별도 API 설계 필요 | Host 프롬프트·도구로 처리 | `input-required` 표준 상태 |
| 사람 작업 완료 감지 | 같은 DB | Webhook 호출 | Host가 2초마다 폴링 | Task 상태 스트리밍 |
| 장애 시 | 프로세스 전체 중단 | 재시도 후 실패, 연동 로그로 추적 | LLM이 오류를 보고 판단·보고 | 카드 수집 실패 → 라우팅 불가로 명확히 실패 |

## 2. 같은 사건, 네 가지 처리: "QA가 v1.0.0 검증을 마치고 이관을 결정했다"

### 2.1 Stage 1 — Standalone

```text
[QA 작업대] Dev 이관 클릭
   └─ workbench.transfer()               같은 프로세스, 같은 DB 트랜잭션
        ├─ issues.status = TRANSFERRED
        └─ cycle.status  = FIXING        → Dev 작업대가 SSE로 즉시 갱신
```

- 연결 비용이 0이다. 대신 Dev와 QA를 따로 배포·운영·확장할 수 없다.

### 2.2 Stage 2 — API

```text
[QA 웹] Dev 이관 클릭
   └─ QA Server: 결정 저장
        ├─ POST {DEV_URL}/api/tickets                          이슈 목록 JSON. QA가 Dev의 주소와 형식을 알고 직접 호출
        └─ POST {DEV_URL}/api/webhooks/verification-completed  검증 결과 통지
             └─ Dev Server: 티켓 생성, 차례 = Dev               실패 시 재시도, 연동 로그 기록
```

- 부서별로 시스템이 분리되었지만, **QA 코드 안에 "이관하면 Dev의 이 API를 이렇게 부른다"는 흐름 지식**이 들어 있다.
- Dev의 API가 바뀌면 QA를 고쳐야 한다. 새 부서가 끼면 호출 체인을 다시 짜야 한다.

### 2.3 Stage 3 — MCP

```text
[QA 웹] Dev 이관 클릭
   └─ QA MCP 서버 DB에 '완료 작업'(outcome: decision=transfer) 기록     QA는 Dev를 모른다
Hub(Host) 2초 주기 폴링: qa__list_completed_work → 발견
   └─ Claude 코디네이터
        ├─ qa__transfer_issues     (이관 데이터 받기)
        ├─ dev__register_tickets   (Dev에 티켓 등록)
        ├─ dev__request_release    (다음 버전 발행 요청)
        └─ qa__ack_work            (전달 완료 처리, 멱등)
```

- Dev와 QA는 서로를 모른다. 연결은 Host의 AI가 **도구(함수)를 하나씩 호출**해 처리한다.
- 흐름 지식이 Host의 프롬프트와 도구 순서에 모인다. 사람의 작업 완료는 Host가 **물어봐야(폴링)** 안다.

### 2.4 Stage 4 — A2A

```text
Hub ── SendStreamingMessage [verify-release] "v1.0.0을 검증해 주세요" ──▶ QA Agent
                                                          Task: working (부서원 판정 대기)
   ◀── status-update "TC-05 FAIL 판정 (김검증)" + metadata.progress     (사람이 일할 때마다 푸시)
[QA 웹] Dev 이관 클릭
   ◀── artifact-update  test-report, issues
   ◀── status-update    completed
Hub 판단(Claude 구조화 출력): transfer_to_dev
Hub ── SendStreamingMessage [fix-and-release] "이슈 3건을 수정하고 차기 버전을 발행해 주세요" ──▶ Dev Agent
```

- Hub는 "검증해 줘", "고쳐서 발행해 줘" 같은 **업무 목표**만 위임한다. 어떻게 검증할지는 QA Agent가 정한다.
- 사람이 몇 분 동안 판정해도 Hub 입장에서는 **working 상태의 Task 하나**이고, 진행 상황은 에이전트가 **먼저 알려 준다**.

## 3. 실측 비교 (같은 시나리오, 지연 0)

| 단계 | mock | LLM (`claude-opus-5-5`) | 상호작용 수 (사이클 1회) |
| --- | --- | --- | --- |
| 1. Standalone | 약 1초 | 약 46초 (LLM 10회) | 함수 호출 |
| 2. API | 약 1초 | 약 34초 | REST 호출 9회 (out 기준) |
| 3. MCP | 약 1초 | 약 48초 (15턴) | MCP 도구 호출 21회 |
| 4. A2A | 약 2초 | 약 50초 (Hub 판단 3회 + 에이전트 문서 작성) | A2A Task 6개 |

읽는 법:

- Stage 3의 21회와 Stage 4의 6개 차이가 **"도구를 쓰는 에이전트(MCP)" 대 "에이전트끼리의 업무 위임(A2A)"** 의 차이다.
- Stage 4의 Task 6개: release-build 1 + verify-release 3 (v1.0.0 / v1.1.0 / v1.2.0) + fix-and-release 2. 승인 회신은 새 Task가 아니라 v1.2.0 검증 Task를 이어 가는 것이다.
- LLM 소요 시간은 단계별로 큰 차이가 없다. 시간은 대부분 LLM이 문서를 쓰는 데 쓰이고, 연결 방식 자체의 비용은 작다.

## 4. 변경에 대한 내성: "보안검토 부서를 추가하라"는 요구가 오면

가상의 요구사항으로 각 구조의 확장성을 비교한다. 검증 통과 후 릴리즈 전에 보안검토 부서의 승인을 받아야 한다고 하자.

| 단계 | 해야 할 일 | 영향 범위 |
| --- | --- | --- |
| 1. Standalone | 보안 서비스 모듈 추가, 사이클 코드의 확정 분기 수정 | 프로그램 전체 재배포 |
| 2. API | 보안 서버 신규 + QA 서버의 "확정 시 호출" 코드를 보안 서버 호출로 수정 + 보안 서버가 결과를 돌려줄 Webhook 설계 | QA 코드 수정, 새 API 계약 2개 |
| 3. MCP | 보안 MCP 서버 신규 + Host 설정에 서버 추가 + 코디네이터 프롬프트에 "확정 결정이면 sec__review를 호출" 규칙 추가 | Host 프롬프트·설정 수정, Dev/QA 수정 없음 |
| 4. A2A | 보안 에이전트 신규(Agent Card에 `security-review` 스킬) + `AGENT_URLS`에 주소 추가 + Hub 워크플로에 단계 추가 | Hub 워크플로 수정, Dev/QA 수정 없음. 보안 에이전트 내부 구현은 자유 |

- Stage 2는 **참여자 간 직접 의존**이 늘어난다. 참여자가 N이면 연결이 최대 N×(N-1)로 늘어난다.
- Stage 3·4는 참여자가 **중앙(Host/Hub)에만** 연결된다. 차이는 중앙이 무엇을 아느냐다. MCP Host는 보안 서버의 **함수들과 호출 순서**를 알아야 하고, A2A Hub는 **"보안검토를 맡긴다"는 업무 단위**만 알면 된다.

## 5. 기술별 장단점 정리

### 5.1 Standalone

| 장점 | 단점 |
| --- | --- |
| 구현·디버깅이 가장 쉽다. 트랜잭션 하나로 일관성 보장 | 부서별 독립 배포·확장·장애 격리가 불가능 |
| 연결 비용(지연, 직렬화, 장애)이 없다 | 조직이 커지면 코드 소유권이 섞인다 |
| 적합: 작은 팀, 단일 시스템, 초기 제품 | 부적합: 여러 조직·회사가 각자 시스템을 운영하는 환경 |

### 5.2 API (REST + Webhook)

| 장점 | 단점 |
| --- | --- |
| 서비스 분리, 언어·배포 독립 | 호출 측이 상대의 URL·스키마·흐름을 알아야 한다 (강한 결합) |
| 성숙한 도구 생태계, 예측 가능한 성능 | 장시간 작업, 진행 알림, 사람 승인 같은 패턴을 매번 직접 설계 |
| 결정적이고 감사하기 쉽다 | 참여자가 늘면 연결과 계약이 급격히 늘어난다 |

### 5.3 MCP (Model Context Protocol)

| 장점 | 단점 |
| --- | --- |
| AI가 도구를 자동 발견(`tools/list`)하고 표준 방식으로 호출 | 관계가 "에이전트 → 도구"로 수직적. 도구 쪽은 수동적이다 |
| 도구 제공자를 한 번 만들면 여러 AI 앱이 재사용 (N×M → N+M) | 흐름 지식이 Host의 LLM·프롬프트에 집중 (세부 함수 호출 21회) |
| 오류를 LLM이 읽고 대응할 수 있다 | 도구가 스스로 진행 상황을 알리거나 되묻기 어렵다. 사람 작업 완료는 폴링으로 확인 |

### 5.4 A2A (Agent2Agent)

| 장점 | 단점 |
| --- | --- |
| 업무 단위 위임, 내부 구현은 불투명(opaque) → 에이전트 교체 자유 | 프로토콜·SDK가 비교적 새롭고, 스트림·Task 상태 관리가 복잡하다 |
| Agent Card로 발견, 스킬 ID로 라우팅 | 스트림이 끊기면 진행 중 Task 복구를 따로 설계해야 한다 (본 구현: Hub 재시작은 GetTask·SubscribeToTask로 복구, 에이전트 재시작은 Task가 메모리에만 있어 실패 처리) |
| 장시간 작업(Task 상태), 진행 알림(스트리밍), 사람 개입(`input-required`), 취소(`CancelTask`)가 표준 | Hub 구성에서는 Hub가 단일 장애점이고 흐름 지식이 Hub에 모인다 |
| 다른 조직·벤더의 에이전트와도 같은 방식으로 협업 | 업무 데이터는 Artifact가 도착해야 보인다 (관찰 시점의 한계) |

## 6. MCP와 A2A는 경쟁이 아니라 보완 관계

```text
                 A2A (에이전트 ↔ 에이전트, 수평)
     ┌──────────────┐  Task / Artifact  ┌──────────────┐
     │  Dev Agent   │ ◀───────────────▶ │  QA Agent    │
     └──────┬───────┘                   └──────┬───────┘
            │ MCP (에이전트 → 도구, 수직)        │ MCP
     ┌──────┴───────┐                   ┌──────┴───────┐
     │ Git, CI, 빌드 │                   │ 테스트 러너,  │
     │ 이슈 트래커   │                   │ 결함 DB       │
     └──────────────┘                   └──────────────┘
```

- MCP는 **한 에이전트가 자기 일을 하기 위해 도구와 데이터에 접근하는 방법**이다.
- A2A는 **각자 일하는 에이전트들이 서로 업무를 주고받는 방법**이다.
- 실제 시스템에서는 둘을 함께 쓰는 것이 일반적이다. 본 프로젝트에서는 선택 과제(A2A + MCP 결합)로 남겨 두었다.

## 7. 어떤 기술을 언제 쓰나

| 상황 | 권장 |
| --- | --- |
| 한 팀이 한 시스템을 만든다 | Standalone (또는 모듈러 모놀리스) |
| 정해진 시스템끼리 정해진 데이터를 주고받는다, 흐름이 고정적이다 | REST API / Webhook / 메시지 큐 |
| AI 애플리케이션이 사내 시스템·파일·DB를 도구로 써야 한다 | MCP |
| 자율적으로 일하는 여러 에이전트(다른 팀·회사·벤더)가 업무를 주고받는다, 작업이 길고 사람 승인이 끼어 있다 | A2A (각 에이전트 내부는 MCP로 도구 사용) |

## 8. 결론

1. **연결 기술은 "누가 흐름을 아는가"를 옮기는 과정이다.** 코드(Standalone) → 각 서비스(API) → 중앙 AI(MCP) → 중앙은 업무 단위만, 방법은 각 에이전트(A2A).
2. **A2A의 핵심 가치는 표준화된 협업 패턴이다.** Stage 2에서 직접 설계해야 했던 장시간 작업, 진행 알림, 승인 요청, 취소가 Stage 4에서는 Task 상태와 스트리밍, `input-required`, `CancelTask`로 표준화되어 있었다.
3. **사람이 일해도 프로토콜은 같다.** 실습 모드에서 부서원이 직접 판정해도 Hub는 데모와 똑같이 Task, 진행 메시지, Artifact만 본다. 에이전트 뒤에 AI가 있든 사람이 있든 협업 방식이 바뀌지 않는다.
4. **대가도 있다.** 비동기 스트림 관리, Task 복구, 중앙 Hub의 단일 장애점은 A2A를 도입할 때 함께 설계해야 할 과제다.
