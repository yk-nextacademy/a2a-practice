## 1. 배경과 목적

### 1.1 업무 배경

소프트웨어 회사에서 흔히 볼 수 있는 부서 간 협업 사이클을 소재로 삼았다.

```text
 개발부서                         검증부서
 ────────                         ────────
 신규 버전 발행  ───────────────▶ 버전 검증 (테스트 실행, 결과 관리)
                                   │
                                   ├─ 문제 있음: 이슈 등록 → 개발부서로 이관
 문제 수정 → 차기 버전 발행 ◀──────┘
                                   └─ 문제 없음: 버전 확정 (릴리즈)
```

이 사이클은 "두 조직이 서로의 결과를 주고받으며 반복한다"는 점에서 시스템 연동 기술을 비교하기에 적합하다.
같은 업무를 연결 방식만 바꿔 4번 구현하면, 기술마다 무엇이 쉬워지고 무엇이 어려워지는지가 분명히 드러난다.

### 1.2 학습 목적

| 목적 | 설명 |
| --- | --- |
| A2A 이해 | 에이전트 간 협업 프로토콜 A2A(Agent2Agent)가 무엇이고 왜 필요한지 실제 동작으로 이해한다 |
| 기술 흐름 이해 | 모놀리식 → REST API → MCP → A2A로 이어지는 연동 기술의 발전 흐름과 각 단계의 한계를 체감한다 |
| 비교 가능성 | 4단계가 **같은 입력에 같은 결과**를 내도록 설계해, 차이가 오직 "연결 방식"에서만 나오게 한다 |
| 실 서비스 감각 | 각 단계를 SQLite 저장소와 웹 대시보드를 갖춘 서비스로 만들어, 사람이 직접 일해 보는 실습이 가능하게 한다 |

### 1.3 결과 요약

| 단계 | 폴더 | 구조 | 실행 결과 |
| --- | --- | --- | --- |
| 1. Standalone | `01_standalone` | 단일 웹 서비스 (8100) | 9/3 → 11/1 → 12/0, APPROVED |
| 2. API | `02_api` | Hub 8200 / Dev 8201 / QA 8202, REST + Webhook | 동일 |
| 3. MCP | `03_mcp` | Hub(MCP Host) 8300 / Dev MCP 8301 / QA MCP 8302 | 동일 |
| 4. A2A | `04_a2a` | Hub(Orchestrator) 8400 / Dev Agent 8401 / QA Agent 8402 | 동일 (사람 승인 후 APPROVED) |

4단계를 동시에 기동해 같은 시나리오를 실행했을 때 모두 같은 결과가 나왔다 (2026-10-15 일괄 점검).

## 2. 업무 시나리오 (전 단계 공통)

### 2.1 등장 요소

| 요소 | 내용 |
| --- | --- |
| 제품 | 로그인(login), 검색(search), 결제(payment), 리포트(report) 4개 기능 |
| 테스트케이스 | 기능별 3개씩 총 12개 (TC-01 ~ TC-12) |
| 결함 | 초기 결함 3개 + 수정 중 생기는 회귀 결함 1개 |
| 버전 | `1.0.0`에서 시작, 발행할 때마다 minor 증가 (`1.1.0`, `1.2.0` …) |
| 이슈 | QA가 FAIL을 근거로 등록 (`ISSUE-1` …). Dev에서는 같은 키의 티켓으로 관리 |

### 2.2 테스트케이스

| ID | 기능 | 이름 | ID | 기능 | 이름 |
| --- | --- | --- | --- | --- | --- |
| TC-01 | login | 정상 로그인 | TC-07 | payment | 카드 결제 |
| TC-02 | login | 세션 유지 | TC-08 | payment | 환불 금액 계산 |
| TC-03 | login | 비밀번호 오류 처리 | TC-09 | payment | 결제 취소 |
| TC-04 | search | 키워드 검색 | TC-10 | report | 일별 리포트 |
| TC-05 | search | 페이지네이션 | TC-11 | report | 결제 합계 리포트 |
| TC-06 | search | 필터 조합 | TC-12 | report | CSV 내보내기 |

### 2.3 결함과 회귀

| 결함 | 영향 TC | 실패 로그 (요약) | 비고 |
| --- | --- | --- | --- |
| D-101 | TC-02 | session expired after 5m (expected >= 30m) | 초기 결함 |
| D-102 | TC-05 | page 2 returned 0 items (expected 20) | 초기 결함 |
| D-103 | TC-08 | refund amount 9999 != 10000 | 초기 결함 |
| D-201 | TC-11 | report total 1,250,000 != payment ledger 1,249,990 | **D-103 수정 시 생기는 회귀 결함** |

환불 금액 절삭 버그(D-103)를 고치면 리포트 합계의 반올림이 어긋나는 회귀(D-201)가 생긴다.
실제 현장에서 자주 일어나는 "고쳤더니 다른 곳이 깨지는" 상황을 재현해, 사이클이 최소 3회 반복되게 했다.

### 2.4 기대 결과

| 회차 | 버전 | 결과 | 처리 |
| --- | --- | --- | --- |
| 1 | v1.0.0 | 9 PASS / 3 FAIL (TC-02, 05, 08) | ISSUE-1, 2, 3 등록 → Dev 이관 |
| 2 | v1.1.0 | 11 PASS / 1 FAIL (TC-11) | ISSUE-1~3 수정 확인(VERIFIED), ISSUE-4 등록 → Dev 이관 |
| 3 | v1.2.0 | 12 PASS / 0 FAIL | ISSUE-4 VERIFIED → 버전 확정 (Stage 4는 사람 승인 후) |

### 2.5 결정적 시뮬레이터

PASS/FAIL은 LLM이 아니라 **순수 함수로 된 시뮬레이터**가 결정한다 (`01_standalone/src/standalone/domain/simulator.py`, 각 단계 `catalog.py`).

```text
run_test(defects, tc)    : 빌드에 남은 결함 중 해당 TC에 영향을 주는 것이 있으면 FAIL + 로그, 없으면 PASS
apply_fixes(defects, tcs): 수정된 TC의 결함을 제거하고, REGRESSIONS 표({"D-103": "D-201"})에 따라 회귀 결함을 추가
next_version("1.0.0")    : "1.1.0"
```

LLM은 이슈 분석, 수정 내역, 릴리즈 노트, 다음 행동 판단 같은 **내용**만 맡는다.
그래서 mock 모드와 LLM 모드의 결과(버전, PASS/FAIL 수, 이슈 수)가 같고, 단계 간 결과를 비교해 이식이 맞았는지 검증할 수 있다.

## 3. 진행 방식: 데모와 실습

모든 단계에 두 가지 진행 방식이 있다.

| 방식 | 시작 버튼 | 누가 일하나 | 용도 |
| --- | --- | --- | --- |
| 데모 | **데모 실행** | 시스템(LLM 또는 규칙)이 처음부터 끝까지 자동 진행 | 전체 흐름 구경, 단계 간 결과 비교 |
| 실습 | **실습 시작** | 부서원 역할의 사람이 웹 작업대에서 직접 발행·판정·이관·수정 | 각 기술에서 "사람의 작업 완료가 상대 부서에 어떻게 전달되는가"를 체험 |

실습 모드 공통 규칙:

- 화면 오른쪽 위 **작업자** 칸에서 지금 누구로 일할지 고른다 (`?as=이름` 링크로도 지정 가능).
- 다른 부서 사람이 작업하면 403, 그 부서의 차례가 아닐 때 작업하면 409로 거절된다.
- QA 판정에서 **실행**은 참고용 자동 실행 결과이고, PASS/FAIL 판정은 사람이 직접 한다. FAIL은 이슈 등록 폼과 함께 처리된다.
- 이슈 내용, 수정 내역, 릴리즈 노트는 **AI 초안** 버튼으로 Claude(또는 mock 템플릿)가 초안을 써 준다.
- 화면에 **차례** 표시가 붙은 부서가 지금 일할 부서다.

| 단계 | 사람의 작업 완료를 상대 부서가 아는 방법 |
| --- | --- |
| 1. Standalone | 같은 프로그램, 같은 DB이므로 즉시 반영 |
| 2. API | 작업한 서버가 상대 서버의 REST API(Webhook)를 직접 호출 |
| 3. MCP | Hub(MCP Host)가 2초마다 MCP 도구로 확인(폴링)하고, 발견하면 AI가 MCP 도구로 전달 |
| 4. A2A | Hub가 위임한 Task가 working 상태로 기다리다가, 완료·진행 상황을 에이전트가 스트리밍으로 먼저 알림 |

## 4. 공통 설계

### 4.1 단계 독립성

- 각 단계는 **완전히 독립 실행**된다. 단계 간 코드 공유가 없고, 단계별로 uv 프로젝트와 DB가 따로 있다.
- 공통 코드(DB, 이벤트, LLM, 웹 계층)는 단계마다 복사해 두었다. 학습자가 한 폴더만 열어도 그 단계를 전부 이해할 수 있게 하기 위함이다.
- 포트 대역이 겹치지 않아 4단계를 동시에 띄울 수 있다 (Stage N → 8N00 대시보드/Hub, 8N01 Dev, 8N02 QA).

### 4.2 폴더 구조

```text
A2A-Practice/
├─ README.md            # 전체 소개, 단계 비교표
├─ TODO.md              # 전체 진행 현황 (마일스톤, 결정 로그)
├─ plan.md              # 초기 기획/설계
├─ docs/                # (본 문서 묶음) 개발 완료 보고서, 기술 비교, A2A 발표 자료
├─ .env.example         # 환경변수 예시 (.env는 git 제외)
└─ 0N_<stage>/
   ├─ README.md         # 실행 방법, 구조, 점검 결과, 학습 포인트
   ├─ pyproject.toml    # uv 프로젝트 ([tool.uv] package = false)
   ├─ run.py            # 단계 전체 기동 진입점 (여러 프로세스 동시 기동/종료)
   ├─ docs/             # PRD.md, TODO.md, USER_SCENARIO.md, images/
   ├─ src/              # 서비스별 패키지
   └─ data/             # 런타임 SQLite DB (git 제외)
```

### 4.3 기술 스택

| 구분 | 사용 기술 | 비고 |
| --- | --- | --- |
| 언어 / 패키지 | Python 3.12, uv 0.13 | 단계별 `.venv`, `uv sync`, `uv run run.py` |
| 웹 | FastAPI, Uvicorn, Jinja2 템플릿 | 서버 렌더링 + SSE 실시간 갱신 |
| 저장소 | SQLite (WAL) | 서비스별 DB 파일, 기동 시 스키마 생성 + 컬럼 마이그레이션(`db.migrate`) |
| LLM | `anthropic` SDK 1.14, 모델 `claude-opus-5-5` | 단순 판단은 effort `low`, server-side fallback 베타 사용 |
| MCP | `mcp` SDK 2.2 (`MCPServer`, `Client`, streamable HTTP) | Stage 3 |
| A2A | `a2a-sdk` 1.1 (protobuf 타입, `create_*_routes`, `[fastapi]` extra) | Stage 4 |
| HTTP 클라이언트 | httpx | Stage 2 연동, Stage 4 감사 로그 래퍼 |
| 화면 점검 | Edge headless, Playwright(Edge 채널) | 스크린샷, 실제 클릭 점검 |

### 4.4 LLM 사용 원칙

| 항목 | 내용 |
| --- | --- |
| 모드 | `LLM_MODE=auto`(기본: 키가 있으면 LLM, 없으면 mock) / `llm` / `mock`, 실행 옵션 `--mock` |
| 역할 | 내용 생성과 판단만 담당. 결과 수치는 시뮬레이터가 결정 |
| 구조화 출력 | JSON 스키마를 지정해 받는다 (이슈 초안, Hub 판단 등) |
| 실패 대비 | 호출 실패나 스키마 불일치 시 같은 자리의 mock 규칙으로 대체하고, 실패 횟수와 마지막 오류를 기록·표시 |
| 키 관리 | 루트 `.env`의 `ANTHROPIC_API_KEY` (임시 키, 구현 완료 후 사용자가 직접 삭제). `.env`, `claudeapi.txt`는 `.gitignore`에 포함 |

### 4.5 UI 원칙

| 원칙 | 내용 |
| --- | --- |
| 스타일 | shadcn/ui 같은 모노톤 디자인, 라이트/다크 전환 |
| 절제 | 기본 제공 이모지 사용 금지. 상태는 배지, 버튼 강조, 배너, 진행 막대로 표현 |
| 실시간 | 서버 이벤트(SSE)를 받으면 화면 일부를 다시 그린다. 입력 중인 폼과 대화상자는 갱신에서 보호(refresh guard, `data-preserve`) |
| 공통 계층 | Stage 2~4는 `common/web`에 `base.html`, `_macros.html`, `app.js`(SSE·갱신), `workbench.js`(작업자 선택·대화상자·AI 초안·실습 API), `app.css`를 둔다 |
| 화면 묶음 | 왼쪽 내비게이션을 업무 / 기록 / 연결(다른 웹으로 이동) 그룹으로 구성 |

### 4.6 운영 규칙

- 기동 시 이전 프로세스에서 끝나지 못한 **데모** 사이클은 CANCELLED 처리한다. 실습 사이클은 사람이 진행하는 것이므로 유지하고 이어서 진행한다 (Stage 3은 Host 재시작 후 폴링 재개, Stage 4는 Hub 재시작 후 진행 중 Task에 GetTask·SubscribeToTask로 다시 붙는다. Stage 4 에이전트가 재시작되면 Task가 사라지므로 사이클을 사유와 함께 실패 처리한다).
- 각 Hub/대시보드에 **사이클 중단**과 **초기화**(전 서비스 데이터 삭제) 버튼이 있다. 중단은 상대 부서 시스템에도 전달되고(Stage 2 Webhook, Stage 3 `cancel_work` 도구, Stage 4 `CancelTask`), 초기화는 진행 중인 사이클이 있으면 거절된다.
- 빌드 산출물은 Dev가 `build_url`(`/builds/{cycle}/{version}`)로 제공하고, QA가 내려받아 검증한다 (전 단계 공통 개념).
