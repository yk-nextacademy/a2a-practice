# User Scenario — Stage 2. API

## 등장인물

| 역할 | 사용하는 웹 | 설명 |
| --- | --- | --- |
| 릴리즈 매니저 / 운영자 | Hub 웹 (8200) | 사이클 시작, 전체 진행·차례 관제, 연동 로그 확인, 초기화 |
| 개발부서원 (최개발, 정개발) | Dev 웹 (8201) | 버전 발행, 접수된 티켓 수정 |
| 검증부서원 (김검증, 이검증, 박검증) | QA 웹 (8202) | 담당 항목 검증, 이슈 등록, 수정 확인, 이관 또는 확정 |

준비: `uv run run.py` 실행. 브라우저 창을 여러 개 열어 역할별로 접속하면 실제 협업처럼 진행할 수 있습니다.
`http://localhost:8200`, `http://localhost:8201/?as=최개발`, `http://localhost:8202/?as=김검증` …

## 시나리오 1. 실습 — 세 웹 서비스로 협업

| 단계 | 담당 / 웹 | 사용자 행동 | 시스템 반응 |
| --- | --- | --- | --- |
| 1 | 매니저 / Hub | **실습 시작** | Hub가 Dev API(`POST /api/cycles?mode=manual`) 호출. Hub 상단 "개발부서 차례", 사이드바 Dev 웹에 "차례" |
| 2 | 최개발 / Dev | 개발 작업대에서 **v1.0.0 발행** | Dev → QA Webhook. QA 웹에 검증 항목 12건 '대기', Hub는 "검증부서 차례" |
| 3 | 김검증 / QA | **내 항목** → TC-01 **실행** → **PASS** | 첫 실행 때 QA가 Dev에서 빌드를 내려받음(Hub Integration에 `GET /builds` 기록). Hub 배너에 "판정 1/12" |
| 4 | 김검증 / QA | TC-02 **실행**(FAIL 로그) → **FAIL** → 이슈 폼 **AI 초안** → **등록 후 FAIL 처리** | QA 시스템에 ISSUE-1 (등록자 김검증) |
| 5 | 이검증·박검증 / QA | 각자 담당 항목 판정, TC-08 FAIL 이슈 등록 | 하단 "검증 완료" 바의 판정 대기 수 감소 |
| 6 | 박검증 / QA | **Dev 이관** → 확인 | QA → Dev `POST /api/tickets`. Dev 웹에 티켓 3건 접수, "차례"가 Dev로 |
| 7 | 최개발·정개발 / Dev | 티켓 **착수** → **수정 완료**(수정 내역, AI 초안) | 티켓 FIXED, 발행 카드에 "반영될 티켓 n건" |
| 8 | 정개발 / Dev | 릴리즈 노트 **AI 초안** → **v1.1.0 발행** | QA 웹 '수정 확인'에 ISSUE-1~3 |
| 9 | 검증부서원 / QA | 재검증, ISSUE-1~3 **수정 확인**, 회귀 TC-11 FAIL 이슈 등록 → **Dev 이관** | ISSUE-4 → Dev 티켓 |
| 10 | 개발부서원 / Dev | ISSUE-4 수정 → **v1.2.0 발행** | QA 차례 |
| 11 | 검증부서원 / QA | 전 항목 PASS, ISSUE-4 수정 확인 → **버전 확정** | QA → Dev 확정 통지, 사이클 "승인" |
| 12 | 매니저 / Hub | Overview, Issues, Integration 확인 | 버전별 결과·QA 결정, QA 이슈와 Dev 티켓 병합 이력, 서비스 간 호출 기록 |

예외 상황:

| 상황 | 시스템 반응 |
| --- | --- |
| QA 웹에서 개발부서원을 작업자로 선택 | 명부에 없음 → "상단에서 검증부서 작업자를 선택하세요" (403) |
| 판정이 남았는데 이관/확정 | 버튼 비활성화, 사유 표시 |
| 실행 결과와 다르게 판정 | "실행 결과와 다름" 표시, 결함은 다음 버전에도 남음 |
| 일부 티켓만 수정하고 발행 | 미완료 티켓은 다음 버전으로 넘어감 (발행 카드 안내). QA는 반영된 이슈만 수정 확인하고, 반영되지 않은 이슈(TRANSFERRED)는 **Dev 이관**으로 다시 넘김. Dev 티켓은 진행 상태·담당자 유지, 중복 생성 없음 |
| 발행/이관/확정 순간 상대 시스템 중지 | 3회 재시도 후 작업 취소, "잠시 후 다시 시도" 안내 (Dev 발행은 저장한 릴리즈를 삭제, 이관·확정은 호출 성공 전에 아무것도 바꾸지 않음) |
| 실습 중 데모 실행 | 409 "이미 진행 중인 사이클이 있습니다" |
| 같은 부서원이 남의 담당 항목 판정 | 서버는 허용(부서 단위 권한, Stage 1과 동일). 화면의 "내 항목" 필터와 행 강조로 안내 |
| Hub/Dev 웹에서 **사이클 중단** | Dev 사이클 CANCELLED → QA에 `cycle-cancelled` 통지 → QA 검증 실행 CANCELLED, QA 작업대에 "중단" 배너 |

## 시나리오 2. 데모 — 자동 Webhook 체인 관찰

| 단계 | 사용자 행동 | 시스템 반응 |
| --- | --- | --- |
| 1 | Hub 웹 **데모 실행** | Dev가 v1.0.0 발행 후 QA에 Webhook |
| 2 | Hub 상단 진행 표시 관찰 | QA의 자동 검증 진행률(QA SSE를 Hub가 중계) |
| 3 | Dev 웹 / QA 웹 열어 보기 | 각 작업대에 "데모 사이클 — 관찰용" 표시, 자기 시스템의 데이터만 보임 |
| 4 | 끝까지 관찰 | v1.1.0(회귀 1건) → v1.2.0 확정. Hub Overview에 버전별 결과 |

## 시나리오 3. 장애 대응

| 단계 | 사용자 행동 | 시스템 반응 |
| --- | --- | --- |
| 1 | QA Server만 중지 | Hub 전 화면 "연동 장애 - QA Server 응답 없음" 배너, Integration에서 QA DOWN |
| 2 | (데모) **데모 실행** | Dev가 Webhook 3회 재시도 후 사이클 FAILED, 오류 배너 |
| 3 | (실습) Dev 웹에서 **발행** | "QA 서버에 발행을 통지하지 못해 발행을 취소했습니다" — 다시 시도 가능 |
| 4 | QA 재기동 `uv run run.py --only qa_server` | 배너 사라짐, 정상 진행. 끝나지 못한 데모 검증 실행은 시작 시 CANCELLED로 정리 |
| 5 | 데모 진행 중 Hub **초기화** 호출 | 1단계 확인에서 409, Dev·QA 어느 쪽도 지워지지 않음 |

## 관찰 포인트 (학습)

- 사이클 상태(차례)는 Dev가, 검증 진행은 QA가 안다. 전체 그림은 Hub가 양쪽을 조회해야 보인다.
- 사람은 자기 부서 웹에서만 일한다. 시스템 사이는 사전에 합의한 연동 API(업무 4개 + 중단 통지 1개)로만 연결된다.
- 경로(어느 API를 언제 부를지)는 코드에 고정되어 있다. 흐름을 바꾸려면 양쪽 시스템을 함께 고쳐야 한다.
