# User Scenario — Stage 1. Standalone

## 등장인물

| 역할 | 설명 |
| --- | --- |
| 릴리즈 매니저 | 데모를 실행하거나 실습을 시작·중단하고, 진행 상황을 관제한다 |
| 검증부서원 (김검증·이검증·박검증) | 검증 작업대에서 담당 항목을 판정하고 이슈를 등록·이관하며 버전을 확정한다 |
| 개발부서원 (최개발·정개발) | 개발 작업대에서 이관된 이슈를 수정하고 차기 버전을 발행한다 |

## 시나리오 0. 실습 모드 — 부서원이 직접 진행

준비: 브라우저 창(또는 기기) 여러 개를 열고 각각 다른 작업자로 접속하면 실제 협업처럼 진행할 수 있습니다.
`/qa?as=김검증`, `/qa?as=이검증`, `/qa?as=박검증`, `/dev?as=최개발`, `/dev?as=정개발`

| 단계 | 담당 | 사용자 행동 | 시스템 반응 |
| --- | --- | --- | --- |
| 1 | 누구나 | 상단 **실습 시작** | 사이클이 '실습'으로 생성, 개발 작업대에 "차례" 표시 |
| 2 | 최개발 | 개발 작업대에서 **v1.0.0 발행** (릴리즈 노트는 비워도 됨) | 검증 작업대에 12개 항목이 '대기'로 생성, "차례"가 검증으로 이동 |
| 3 | 김검증 | **내 항목** 탭 → TC-01 **실행** → 결과 PASS 확인 → **PASS** | 판정 진행 1/12, 다른 부서원 화면에도 실시간 반영 |
| 4 | 김검증 | TC-02 **실행** → FAIL 로그 확인 → **FAIL** | 이슈 등록 폼: 제목·로그가 미리 채워짐. **AI 초안**으로 제목·설명·심각도 작성 → **등록 후 FAIL 처리** → ISSUE-1 |
| 5 | 이검증, 박검증 | 각자 담당 항목 판정, TC-08 FAIL은 이슈 등록 | 하단 "검증 완료" 바의 판정 대기 수가 줄어듦 |
| 6 | 검증부서원 | 모든 항목 판정 후 **Dev 이관** → 확인 | 이슈 3건 TRANSFERRED, "차례"가 개발로 이동 |
| 7 | 최개발 / 정개발 | 이슈마다 **착수** → **수정 완료** (수정 내역 입력 또는 AI 초안) | 이슈 FIXED, 발행 카드에 "수정 완료된 이슈 n건이 반영됩니다" |
| 8 | 정개발 | 릴리즈 노트 **AI 초안** → **v1.1.0 발행** | 검증 차례. '수정 확인' 카드에 ISSUE-1~3 |
| 9 | 검증부서원 | 항목 재검증, ISSUE-1~3 **수정 확인**, 새로 깨진 TC-11(회귀)은 FAIL + 이슈 등록 → **Dev 이관** | ISSUE-4 등록 |
| 10 | 개발부서원 | ISSUE-4 수정 → **v1.2.0 발행** | 검증 차례 |
| 11 | 검증부서원 | 전 항목 PASS, ISSUE-4 수정 확인 → **버전 확정** | 사이클 "승인", v1.2.0 확정 |

예외 상황:

| 상황 | 시스템 반응 |
| --- | --- |
| 작업자를 선택하지 않거나 다른 부서원으로 작업 | 작업대 상단 "작업자 확인" 안내, 서버는 403 "검증부서 작업자만 할 수 있는 작업입니다" |
| 판정이 남았는데 이관/확정 | 버튼 비활성화, 사유 표시 ("판정하지 않은 항목이 n건 있습니다") |
| 미해결 이슈가 있는데 확정 | 확정 불가 — 이관해야 함 |
| 실행 결과는 FAIL인데 PASS로 판정 | 판정 옆에 "실행 결과와 다름" 표시. 판정은 사람의 결정으로 존중되며, 결함은 다음 버전에도 남는다 |
| 일부 이슈만 수정하고 발행 | 미완료 이슈는 다음 버전으로 넘어감 (발행 카드에 안내). 검증부서는 해당 항목을 FAIL(기존 이슈에 연결)로 판정한 뒤 **Dev 이관**으로 다시 개발부서 차례를 만들고, 미완료 이슈는 상태·담당자 그대로 이어서 수정됨 (예: 9/3 → 10/2 → 11/1 → 12/0) |
| 이미 미해결 이슈가 있는 항목을 FAIL 처리 | 이슈 등록 폼에 "연결" 안내. 새 이슈 대신 기존 이슈에 연결 |
| 수정 확인 대기(FIXED) 이슈가 있는 항목을 FAIL 처리 | 이슈 등록 폼에 "수정 확인 대기" 안내 — 수정이 안 되었다면 '수정 확인' 카드의 **재현**을 누른다 (폼에서 등록하면 새 이슈가 생김) |
| 실습 중 데모 실행 | 데모 버튼 비활성화 (API는 409) |
| 실습 중 초기화 | 초기화 버튼 비활성화 (API는 409). 실습 기록을 지우려면 먼저 실습을 끝내거나 중단 |
| 실습 중단 | 상단 **실습 중단** → 확인 → 사이클 '중단', 기록 유지 |

## 시나리오 1. 데모 실행 (자동 흐름)

| 단계 | 사용자 행동 | 시스템 반응 |
| --- | --- | --- |
| 1 | `uv run run.py` 실행 후 `http://localhost:8100` 접속 | Overview에 "아직 실행된 사이클이 없습니다" 안내 |
| 2 | 상단 **데모 실행** 클릭 | 버튼이 "데모 실행 중"으로 바뀌고 비활성화. 토스트 "사이클 시작" |
| 3 | Overview 관찰 | 파이프라인의 **발행** 단계 강조 → Dev가 v1.0.0 발행 (토스트 "릴리즈 발행") |
| 4 | 상단 진행 표시 관찰 | "테스트 실행 5/12 · TC-05 FAIL" 형태로 진행률 표시 |
| 5 | 최근 이벤트 관찰 | `ISSUE-1~3 등록` 이벤트. LLM 모드면 로그를 분석한 제목·설명·심각도가 기록됨 |
| 6 | 계속 관찰 | **이관** → **수정** 단계로 이동, Dev가 수정 내역 작성 후 v1.1.0 발행 |
| 7 | 계속 관찰 | v1.1.0 검증에서 회귀 결함 1건(TC-11) 발견 → ISSUE-4 등록, ISSUE-1~3 VERIFIED |
| 8 | 계속 관찰 | v1.2.0 발행 → 12건 전체 PASS → 토스트 "릴리즈 승인", "사이클 완료" |
| 9 | Overview 확인 | 상태 "승인", 현재 버전 v1.2.0, 통과율 100%, 버전별 결과 막대 3개 |

## 시나리오 2. 결과 상세 확인

| 단계 | 사용자 행동 | 확인 내용 |
| --- | --- | --- |
| 1 | **Releases** → `v1.1.0` 선택 | LLM이 작성한 릴리즈 노트, 반영된 ISSUE-1~3과 수정 내역, 이 버전에서 발견된 ISSUE-4 |
| 2 | **Test Runs** → Run #2 선택 | 테스트 매트릭스(12칸 중 TC-11만 채워짐), 실패 로그 |
| 3 | **Issues** → `ISSUE-3` 선택 | 설명, 수정 내역, 상태 이력 `OPEN → TRANSFERRED → IN_PROGRESS → FIXED → VERIFIED` 와 담당(QA/Dev) |
| 4 | **Timeline** | 사이클 전체 이벤트를 시간 역순으로 확인. `Simulator` 행은 숨은 회귀 결함 발생을 학습용으로 보여줌 |

## 시나리오 3. 예외 상황

| 상황 | 사용자 행동 | 시스템 반응 |
| --- | --- | --- |
| 중복 실행 | 실행 중 데모 실행 API 재호출 | 409, 토스트 "시작할 수 없음 — 이미 진행 중인 사이클이 있습니다" |
| 이력 조회 | Overview 사이클 이력에서 이전 사이클 행 클릭 | 해당 사이클 기준으로 모든 화면 조회 (`?cycle=N`) |
| 초기화 | 진행 중인 사이클이 없을 때 **초기화** → 확인 대화상자에서 **초기화** | 모든 데이터 삭제 후 빈 Overview (진행 중인 사이클이 있으면 버튼 비활성화, API 409) |
| LLM 장애 | API 키 오류/네트워크 장애 | 해당 작업만 mock 결과로 대체, 사이클은 계속 진행 (`/api/state`의 `failures` 증가) |

## 관찰 포인트 (학습)

- 사이클 진행 순서는 `services/cycle.py`에 고정되어 있다. "검증 → 이관 → 수정"의 순서를 바꾸거나 승인 절차를 추가하려면 코드를 수정해야 한다.
- 이슈 상태 이력의 담당자가 QA와 Dev로 번갈아 나타나지만, 실제로는 같은 프로세스가 같은 테이블을 수정한다.
